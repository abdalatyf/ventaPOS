# VentaPOS Unified API Contract & Architecture Specification

## 1. Core Data Models
### 1.1 Receipt & Installments
- **Receipt**: Tracks a customer sale. Features `total_amount`, `down_payment`, `receipt_number`, `branch_id`, `receipt_hash` for integrity, and `is_confirmed` to track verification status of mobile-pushed receipts.
- **InstallmentPayment**: Linked to Receipt. Fields: `payment_date`, `amount`. Always anchors on the 25th of the month.
- **Clean Slate Rule**: When updating a Receipt, all existing items and payments MUST BE DELETED and recreated in bulk. Do not attempt surgical updates.

### 1.2 Inventory & Pricing Time Machine
- **InventoryItem**: Uses `initial_quantity`, `initial_month`, `initial_year`. Stock is calculated dynamically at runtime via `get_stock_at_date()`.
- **CommissionHistory**: Maintains historical integrity. Commissions are queried via `get_commission_at_date(month, year)`.

## 2. API Endpoints (Frontend Consumption)
### 2.1 Autocomplete Services
- `GET /api/product-suggestions/?term={term}&month={m}&year={y}`
  - Returns: `[{"id": int, "text": string, "price": float}]`
- `GET /api/customer-suggestions/?term={term}&field={type}&salesperson_id={id}`
  - Returns: `[{"id": string, "text": string}]`

### 2.2 Core Actions
- `POST /receipts/add/`
  - Payload: Form data with dynamically generated `item_X` and `qty_X` fields, along with `down_payment`.
- `POST /receipts/print_batch/`
  - Payload: `{selected_printer, offset, limit}`
  - Note: Frontend MUST enforce a 3000ms delay between batch calls to prevent Windows Spooler crashing.

## 3. Server Sync APIs
- `POST /api/v1/sync/push/`
  - Purpose: Push data from Desktop to Server. Receipts are saved with `is_confirmed = True`.
- `POST /api/v1/sync/mobile-push/`
  - Purpose: Push data from Mobile to Server. Receipts default to `is_confirmed = False`.
- `GET /api/v1/sync/pending-receipts/`
  - Purpose: Fetch unconfirmed receipts pushed from Mobile for a specific branch.
  - Params: `?machine_id={id}`
  - Returns: `{ "status": "success", "pending_receipts": [...] }`
- `POST /api/v1/sync/confirm-receipts/`
  - Purpose: Confirm pending receipts from the Desktop app.
  - Payload: `{ "machine_id": "...", "receipt_hashes": ["hash1", "hash2"] }`

### 3.1 Remote Provisioning APIs
- `POST /api/v1/sync/upload-setup/`
  - Purpose: Desktop app pushes salesperson's `setup.json` payload.
  - Payload: `{ "machine_id": "...", "payload": { ... } }`
  - Returns: `{ "status": "success", "token": "uuid" }`
- `GET /api/v1/sync/download-setup/`
  - Purpose: Mobile app downloads `setup.json` payload using a one-time token.
  - Params: `?token={token}`
  - Returns: `{ "status": "success", "payload": { ... } }` (and immediately deletes the token)

## 3. Security & Licensing Constraints
- **Hardware Binding**: License validation is strictly bound to the hardware signature generated by `wmic csproduct get uuid`.
- **Decorators**: Frontend routes MUST be guarded by `@branch_required` and, where applicable, `@pro_plan_required`.
- **Database Decryption**: The AES/Fernet layer runs ONLY at `run_app.py` startup, extracting `business_data.enc` to `~sys_runtime_cache_v1.tmp` in WAL mode. No frontend UI has access to raw `.enc` files.
